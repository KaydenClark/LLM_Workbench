# A release is proven by the Template taking a confirmed concept through the five parent workflows in one pass

Landmark: Workbench Template.

1. Among its other gates, a Workbench release is proven when the Template, updated to that release and deployed in the cloud, is run through a grilling session from a prewritten grill-me-and-genesis script and produces the website asked for, correctly, without being blocked by anything that should not block it. It must take the whole workflow in a single pass, through the five parent workflows the owner confirmed: Explore (Idea → Align → Confirm), Promote (Record → Publish → Map → Publish → Plan → Publish), Journey (Implement → Check → QA → Submit), Judge (Review → Verify → Approve) and Complete (Delivered → Clean Up), with no second Align; the owner's only step is Approve, judging whether the website is viable. Judge and Complete group existing steps without changing their gates; Confirm finishes Explore, and Promote starts from the confirmed concept.

2. The release proof builds Puffer Pond (github.com/KaydenClark/Puffer-Pond), the small full-screen living pond illustration, from the prewritten grilling script, with the Template deployed in the cloud.

Why the owner chose it:

- The owner, in his own words (2026-10-03, teardown round 1): "The idea is the workbench can take a do the workflow in a single pass ... without a second align needed. It theorectically should just be the human QA step."
- The owner (teardown round 1): "when I can effortless algin my design concepts into products, where I Align confirm. and come back to a finished product to approve"
- For the Puffer Pond choice, the owner's confirmed reason: A website is a product the owner can judge viable by using it, so Approve stays the owner's only step, and running it in the cloud from a script proves the pass needs nothing from the owner's machine or memory.
- The verb list is the owner's answer to the Grill Board question "Correct the release proof decision record's verb list" (GB-0026, verdict Change, 2026-10-09T02:07Z): his note is the five-parent-workflow map above, and in chat the same day he confirmed it is his answer: "yes. that map is." The map is the one the owner confirmed for the Runbook's Workflows reference on 2026-10-08.

Considered and rejected: Keeping the earlier list (Idea, Align, Confirm, Journey, Complete, with Journey as Map, Plan, Implement, Review and Verify). It named a verb the owner replaced with Delivered on 2026-10-03 and a Journey the owner reshaped on 2026-10-05 (Implement, Check, QA, Submit, with Review after it), so the proof plan would have run a workflow that no longer exists. Also rejected: editing the earlier record in place, because a decision record is corrected only by a visible successor.

Consequences: The release proof, owned by Template Release Proof: Puffer Pond (S-004I), runs the five parent workflows as the Runbook's Workflows reference lines them up, and the gate in Workbench Terms And Workflow Verb Rows (S-004G) that waited on this correction closes. How this proof relates to the existing Template upgrade release gate is still the release-proof Spec's to state. The Blueprint's promised outcome that every release is proven by a Template-made project taking a confirmed concept to the owner's approval in one pass is unchanged, so BLUEPRINT.md stays the owner named in canonicalized_in.
